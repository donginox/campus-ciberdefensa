ALAMEDA: recibir, analizar y documentar evidencia propia

Material ficticio y benigno de Campus. Trabajá en una carpeta de práctica sobre copias de los archivos exportados. Campus no adquiere evidencia de tu equipo ni instala herramientas. Registrá cualquier fuente o herramienta que no puedas analizar; ese límite forma parte del informe.

1. Registrar recepción y hashes

  1. Exportá el ZIP de disco desde Campus. Si la distribución lo ofrece, exportá también el ZIP nativo. Anotá fecha UTC, versión de Campus, origen, nombre y tamaño de cada paquete.
  2. Conservá una copia original y extraé una copia de trabajo en otra carpeta. Dentro del ZIP de disco, compará las huellas con SHA256SUMS.txt y manifest.json. El ZIP nativo tiene su propio manifest.json.
  3. Calculá hashes antes y después del análisis. Un hash consistente prueba igualdad de bytes; por sí solo no autentica autoría ni veracidad.

Windows · PowerShell, dentro de tu carpeta de copia

Get-FileHash -LiteralPath .\alameda-fat16.img -Algorithm SHA256
Get-FileHash -LiteralPath .\campus-owned-process.dmp -Algorithm SHA256
Get-FileHash -LiteralPath .\campus-training.evtx -Algorithm SHA256

Linux · dentro de tu carpeta de copia

sha256sum -c SHA256SUMS.txt
sha256sum campus-owned-process.dmp campus-training.evtx

Los archivos nativos solo están en el paquete separado. Si no los recibiste, documentá esa ausencia. Para esos archivos compará cada salida con su manifiesto nativo, no con SHA256SUMS del disco.

2. Analizar el sistema de archivos y recuperar una entrada

Windows · Autopsy o FTK Imager

Creá un caso nuevo en una carpeta de trabajo. Agregá la copia de alameda-fat16.img como imagen de disco/raw; no como disco físico. Elegí offset 0 si la herramienta lo solicita. En una versión que reconozca FAT16, revisá entradas activas y borradas y exportá la entrada borrada a otro archivo. Registrá herramienta/versión, nombre parcial, tamaño, metadatos y hash del contenido recuperado. Las marcas FAT no guardan zona horaria: UTC es una convención declarada por el generador, no algo probado por el sistema de archivos.

Linux · Sleuth Kit instalado por vos

fls -V
fls -f fat -o 0 -r alameda-fat16.img
fls -f fat -o 0 -d alameda-fat16.img

Tomá el identificador de metadatos de la entrada borrada que muestra fls. Sustituí IDENTIFICADOR por ese valor en la siguiente plantilla; no es una orden lista para copiar:

icat -r -f fat -o 0 alameda-fat16.img IDENTIFICADOR > recuperado.txt
sha256sum recuperado.txt

No montes la imagen con escritura. Compará lo recuperado con otras fuentes sin equiparar presencia de un archivo con lectura, ejecución o exfiltración. Si tu versión no reconoce FAT16, registrá el error y consultá sus formatos compatibles.

Referencias de método: guía de Autopsy, fls y icat.

3. Inspeccionar el minidump de proceso

En Windows abrí la copia del DMP con WinDbg mediante la opción para abrir un dump (el nombre de menú depende de la versión). Anotá el tipo y alcance que informa el depurador, las regiones disponibles y las limitaciones de símbolos. Buscá cadenas del escenario propio y registrá dirección/offset o procedimiento de búsqueda, junto al contexto observado. No necesitás conectarte a un servidor de símbolos para citar una cadena en los bytes del archivo.

En Linux un lector de minidump compatible permite inspeccionar sus estructuras. Un visor de cadenas solo permite una observación limitada. Por ejemplo, strings -a campus-owned-process.dmp puede mostrar texto ASCII; conserva también texto de módulos y no prueba que una instrucción se ejecutó. Distinguí archivo completo, región capturada y estado del proceso.

Volatility necesita un formato de memoria, capas y símbolos compatibles. Este minidump de proceso no se ofrece como imagen de RAM para Volatility. Si tu objetivo es practicar análisis de memoria completa con ese framework, necesitás otra adquisición propia y compatible: esa práctica queda fuera de este paquete.

Referencia: análisis de dumps de usuario con WinDbg.

4. Leer eventos nativos y comparar procedencias

En Windows abrí el archivo EVTX guardado con Visor de eventos. Revisá proveedor, canal, IDs, hora, mensaje y metadatos de captura. También podés leer únicamente el archivo recibido:

wevtutil qe .\campus-training.evtx /lf:true /f:xml

En Linux podés usar un lector EVTX que ya tengas y que admita el formato, o analizar el XML distribuido como fuente derivada. Anotá cuál usaste; leer XML no equivale a verificar el binario EVTX con un parser independiente. El proveedor puede no estar instalado y el mensaje descriptivo puede no resolverse; los campos XML siguen disponibles. No importes esos eventos a los registros de tu sistema.

Compará actor, IP y reloj de EVTX/XML frente a JSONL y CSV. No impongas una relación causal entre capturas de distinta procedencia. Referencia: wevtutil.

5. Ingerir y contrastar reglas en Campus

  1. Ingerí ALAMEDA. Probá filtros exactos por clase, actor e IP y anotá consulta, IDs y resultado.
  2. Repetí la ingesta para comprobar que los mismos IDs no se duplican. Reiniciar el índice elimina eventos y detecciones de ese perfil; conservá primero el JSONL original.
  3. Contrastá cada detección con sus IDs de evidencia. El motor usa dos reglas fijas: tres fallas previas y éxito dentro de cinco minutos del mismo actor/IP; acceso al servidor después de éxito en salto del mismo actor/IP, también dentro de cinco minutos.
  4. Usá Transferencia para probar la misma lógica con otro actor/IP. Es una variante de eventos; no constituye otra triada independiente de disco/memoria/red.

Para importar tus eventos de laboratorio, seleccioná un JSONL mediante el diálogo nativo. Cada línea debe ser un objeto con exactamente id, time, kind, actor, sourceIp, host, detail. Hora UTC ISO con milisegundos; IP válida; clases: auth.failure, auth.success, service.access, network.connect o file.read. No se aceptan comandos ni SQL. Los JSONL sintéticos distribuidos cumplen ese esquema; EVTX, XML y CSV requieren una normalización explícita y no se importan directamente.

Límites: 5000 eventos por perfil, 2 MiB por importación, 16 MiB por índice y 200 filas por consulta. Un ID idéntico es idempotente; el mismo ID con contenido diferente rechaza la ingesta. Copiar o combinar el perfil entre Windows y Kali lleva informes y borradores, pero no el índice SQLite ni los discos de las VMs. Conservá los JSONL y ZIP fuente para reingerir y verificar la evidencia en el otro equipo.

6. Entregar una conclusión revisable

En Campus completá custodia, disco, memoria, eventos, red, conclusión y ayuda recibida. Separá hechos observados de hipótesis, explicá una alternativa y proponé la próxima comprobación. Para cada afirmación indicá archivo y referencia verificable: hash, ID de evento, metadato, offset o consulta. Mencioná las herramientas y fuentes que faltaron.

La primera entrega queda inmutable. Las revisiones se guardan en un borrador separado. La orientación se habilita después de guardar la entrega y registra ayuda consultada. La corrección es una autoevaluación docente: ni una detección ni un informe completo acreditan preparación automática para una certificación.
